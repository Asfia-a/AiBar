# 酒馆聊天能力对标与提示词引擎方案

> 对标对象：SillyTavern（酒馆）Chat Completion 模式的聊天链路
> 盘点时间：2026-10-23　范围：聊天与提示词构建，不含 TTS / 图片生成 / 扩展商店

---

## 1. 酒馆的提示词拼装顺序（基准）

Chat Completion 模式下，酒馆把上下文按固定顺序拼成 messages，各段都可独立开关与调序：

```
[Main Prompt]            系统级身份与总体规则
[World Info · before]    命中关键词的世界书条目（角色定义之前）
[Persona Description]    用户人设
[Char Description]       角色描述
[Character Personality]  性格
[Scenario]               场景
[Author's Note · after]  作者注释（角色定义之后）
[Examples]               示例对话
--- New Chat 分隔 ---
[Chat History]           历史消息，其中可插入 in-chat 深度注入
[Post-History Instructions] 最后一句强指令
```

关键点：**位置比内容更重要**——越靠近上下文末尾，对模型这次回复的影响越大。

## 2. 差距对照表

| 能力 | 酒馆的做法 | 我们的现状 | 等级 |
|---|---|---|---|
| 世界书 World Info | 关键词触发、扫描深度、token 预算、递归激活、插入位置/顺序、常量条目、触发概率、包含组、粘滞/冷却 | 无 | **P0** |
| 作者注释 Author's Note | 一段话插到任意位置（角色定义后 / 历史第 N 条之前），可设每 N 轮插入一次 | 无 | **P0** |
| 提示词管理器 | 提示块命名、role 可改、拖拽排序、按触发类型（普通/重写/续写）生效 | 硬编码在 `ChatService` 的 StringBuilder 里 | **P0** |
| 格式模板 | 世界书、场景等用模板包裹后再注入 | 无 | P1 |
| Post-History Instructions | 上下文最后一句强指令 | 无 | P1 |
| 采样参数 | temperature / top_p / top_k / presence / frequency / repetition / stop | 只有 temperature、top_p、max_tokens | P1 |
| 消息操作 | 滑动重生（swipe）、编辑、分支 | 只有「重新生成」 | P1 |
| 角色卡字段完整度 | V2/V3 卡：mes_example、system_prompt、post_history_instructions | 有 greeting / exampleDialogue，缺 system_prompt | P1 |
| 群聊 | 多角色轮流发言、发言顺序策略 | 无 | P2 |
| 长期记忆 | 摘要记忆 + 向量检索（Data Bank） | 只有窗口裁剪 | P2 |
| 正则替换 | 发送前/接收后正则改写 | 无 | P2 |
| 快捷回复 / STscript | 斜杠命令、自动化 | 无 | P2 |

**结论**：聊天手感上差得最远的不是模型，而是这三件——世界书、作者注释、可编排的提示词层。这三样补齐后，同样的模型答出来的东西会明显不一样。

## 3. 本轮落地的框架

```
ChatService
   └─ PromptEngine.build(PromptInput)
        ├─ PromptTemplateService   加载 classpath:/prompts/*.md，替换 {{char}} {{user}} {{time}}
        ├─ WorldInfoService        关键词激活 + 预算裁剪 + 递归一层
        └─ TokenBudget             按段分配额度，超预算先裁历史
   → PromptBundle(messages, 统计信息)
```

### 3.1 拼装顺序（与酒馆对齐）

```
system:  主提示（模板 + 角色卡设定）
system:  世界书（before_char）
system:  作者注释（after_char）
history: 对话历史
   └─ in-chat 注入：作者注释 / 世界书条目按 depth 插到倒数第 N 条之前
system:  Post-History Instructions（可选）
```

### 3.2 世界书激活算法

```
输入：候选条目、最近 N 条消息拼成的扫描文本、预算 B
1. 常量条目（constant=1）先进，按 order 升序
2. 关键词命中：keys 任一出现在扫描文本中（对中文关闭全词匹配）
3. 按 order 升序、预算 B 贪婪装入，超预算即停
4. 递归一层：新装条目的 content 里若提到其它条目 keys，再尝试装入（同样受预算约束）
5. 概率过滤：probability < 100 时按概率丢弃
```

### 3.3 作者注释

- 内容、位置（after_char / in_chat + depth）、频率（每 N 条用户消息插一次）存在会话上
- 会话未设置时回落到角色卡默认值

## 4. 用不起官方 API 怎么办

现在的 `AiModelService` 已经支持 OpenAI 兼容协议 + base_url 热切换，可以这样降成本：

| 场景 | 做法 | 成本 |
|---|---|---|
| 日常开发联调 | 不配 Key，走已有的本地模拟流式 | 0 |
| UI / 交互调试 | 同上，只验交互不验内容 | 0 |
| 提示词调优 | 本地 Ollama（`http://127.0.0.1:11434/v1`，qwen2.5:7b 之类） | 0 |
| 答辩演示 | 便宜模型 + 世界书按需激活，只带命中的条目 | 极低 |
| 出图 / 长文 | 单独跑几次，平时不开 | 按次 |

省 token 的三个开关（本轮已具备）：
1. **世界书按需激活**：没命中的条目根本不进 prompt，比把设定全塞进去省一大截。
2. **分层预算**：system / 世界书 / 作者注释 / 历史 / 输出各占额度，超了先裁最早的历史。
3. **作者注释按频率注入**：默认每轮都插，可以设成每 3 轮插一次，长会话省 2/3。
